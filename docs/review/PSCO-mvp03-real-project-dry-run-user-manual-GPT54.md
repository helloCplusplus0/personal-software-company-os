## 2. PSCO 到底是什么

### 2.1 产品定位

PSCO 是一个面向个人软件公司的**经营与资产系统**。

它的核心命题不是“帮你管理代码”，也不是“替你自动规划一切”，而是：

> 让你围绕真实软件项目，持续进行资产登记、周期性 review、决策留痕、实体回流与复用加速。

换句话说，PSCO 的设计目标是帮助你完成下面这件事：

1. 把项目资产登记清楚；
2. 周期性回来看当前焦点、反馈与待处理决策；
3. 在 review 中形成下一步动作；
4. 把动作回流到 `Decision / Product / Module / Repository`；
5. 逐渐让复用与派生提示减少下一次创造的启动成本。

### 2.2 PSCO 不是什么

为了避免 `dry-run` 时使用预期跑偏，先明确 PSCO 现在不是什么：

- 不是通用任务管理器
- 不是代码托管平台
- 不是自动扫描与知识图谱系统
- 不是 AI Chat / AI Agent 工作台
- 不是完整模板平台
- 不是已经进入 `mvp0.4+` 的 Venture / Opportunity / Experiment 系统

如果用一句话讲：

> 当前阶段的 PSCO，更像是“围绕真实软件项目进行周期性经营的驾驶舱 + 资产回流系统”。

## 3. PSCO 的核心对象与职责

### 3.1 Dashboard

`Dashboard` 是当前正式经营入口，不只是总览页。

它的职责是：

- 提供 `Daily Review` 与 `Weekly Review` 的明确入口
- 展示系统概览、当前焦点、反馈信号、最近活动与复用快照
- 作为 review 与各 canonical owner 页之间的统一起点和回流点

**正确理解：**  
你不应该把 Dashboard 只当成“看一眼数字”的页面，而应该把它当成“决定今天或这周下一步做什么”的入口。

### 3.2 Daily Review

`Daily Review` 的职责是处理**今天必须判断或推进的焦点**。

它重点承接：

- `Current Focus`
- `待处理决策`
- `代表性反馈信号`
- 底部统一动作区

Daily Review 更偏向“今日分诊”和“快速推进”。

### 3.3 Weekly Review

`Weekly Review` 的职责是做**本周盘点、整理和下一次创造准备**。

它重点承接：

- 系统概览
- 模板候选
- 派生智能提示
- 最近活动
- 代表性反馈
- 复用感知快照
- 底部统一动作区

Weekly Review 更偏向“阶段性盘点 + 结构化下一步发现”。

### 3.4 Decision Center

`Decision Center` 不是备注列表，而是经营回路中的正式决策承接位。

当你在 review 中觉得“这件事需要明确判断、留痕或形成行动共识”时，应进入 `Decision Center`。

### 3.5 Product Registry

`Product Registry` 承接产品级实体信息，尤其是：

- 产品登记
- 基于模板的创建预填
- 查看模板来源摘要
- 查看绑定模块与仓库
- 作为“下一次创造”的主要承接位

### 3.6 Module Registry

`Module Registry` 承接模块资产的登记、查看与从派生提示进入的能力补齐动作。

当前它也是 `capability_gap_hint` 的主要承接位。

### 3.7 Repository Binding

`Repository Binding` 承接仓库登记与产品/仓库之间的绑定关系。

当前它不是 review 的主线入口，但仍是经营闭环里的正式实体页。

### 3.8 Template Reuse / Derived Intelligence

它们当前不是独立一级平台，而是 review 的支撑层。

- `Template Reuse`：把已有 `Module` 组合转成下一次创建 `Product` 的低摩擦起点
- `Derived Intelligence`：给出复用机会与能力缺口提示，帮助判断“下一步该复用什么、补齐什么、推进什么”

## 4. 使用前准备

在开始真实 `dry-run` 之前，建议先确认以下最小前提：

1. 系统里至少已有一部分真实或半真实的 `Product / Module / Repository / Decision`
2. `Dashboard` 能看到概览、焦点、信号与活动，不是全空系统
3. 至少存在一组有复用可能的模块组合，这样 `Weekly Review` 才有模板候选意义
4. 你准备以一个真实项目为中心进行使用，而不是随机点功能

如果系统当前几乎没有数据，`dry-run` 很容易退化成“在空系统里点页面”，那样得到的反馈质量会很低。

### 4.1 `dry-run` 进入前检查清单

正式开始前，建议先按下面清单自检；如果存在 `2` 项以上未满足，建议先不要开始正式 `dry-run`，而是先补齐前置数据或环境。

- [ ] 当前前后端环境已稳定运行，且你准备在同一环境内完成本轮使用
- [ ] 至少已存在一个真实或半真实项目主线，不是完全空库
- [ ] `Dashboard` 可见概览、焦点、信号、活动，不是整页空态
- [ ] 至少存在一个可被 review 消费的待处理事项：`Decision / Product / Module / Repository` 任一即可
- [ ] 若要验证模板复用，则至少已有一组可形成候选的模块组合
- [ ] 你已经明确本轮 `dry-run` 想回答的核心问题，例如“是否真的帮助推进今天的项目判断”或“模板是否明显减少新建成本”
- [ ] 你准备记录本轮路径、感受与证据，而不是只凭结束后的印象回忆

### 4.2 本轮目标先写清楚

开始前，建议你先用一句话写下本轮目标，例如：

- 今天我要用 PSCO 帮我判断这个真实项目当前最该推进什么
- 这周我要验证模板复用是否真的让我更快开启下一次创造
- 我要确认 `Decision` 是否真的能成为 review 的正式承接位

如果没有先写清楚本轮目标，`dry-run` 很容易退化成“功能浏览”，而不是“真实经营验证”。

## 5. 标准使用节奏

### 5.1 日常节奏

推荐日常主线：

`Dashboard -> Daily Review -> Decision / Product / Module / Repository -> 返回 Dashboard`

适用场景：

- 今天需要判断当前最重要的焦点
- 需要处理待决策事项
- 需要基于反馈推进某个实体动作

### 5.2 周期性节奏

推荐每周主线：

`Dashboard -> Weekly Review -> Template Candidates / Derived Hints -> Product Create / Module Registry -> Product Detail / Module Detail -> 返回 Dashboard`

适用场景：

- 盘点现有资产与反馈
- 判断是否有复用机会
- 判断是否存在能力缺口
- 基于已有模板更快开启下一次创造

### 5.3 何时进入 Review

推荐这样理解：

- `Daily Review`：回答“今天最该推进什么？”
- `Weekly Review`：回答“这周系统告诉我下一步最值得做什么？”

如果你只是想直接查某个产品或模块，也可以直接进入相应 registry；但只要你想让 PSCO 发挥“经营系统”的价值，还是应优先从 `Dashboard -> Review` 进入。

## 6. 标准操作手册

## 6.1 从 Dashboard 开始

### 应该怎么看

进入 `Dashboard` 后，推荐按这个顺序看：

1. 顶部 `Daily Review / Weekly Review` 双入口
2. 概览条带
3. `Current Focus`
4. `Asset Feedback`
5. `Recent Activity`
6. 复用快照与数据主权入口

### 应该怎么用

如果你是要处理**当天推进**，点 `Daily Review`。  
如果你是要处理**本周盘点 / 复用 / 下一次创造**，点 `Weekly Review`。

### 你不应该怎么用

不要把 Dashboard 只当成“看数字的首页”。  
PSCO 目前的设计意图，是让 Dashboard 成为经营动作入口。

---

## 6.2 Daily Review 标准用法

### 页面结构

`Daily Review` 现在可以理解成三段：

1. 焦点与信号区  
   - `Current Focus`
   - `待处理决策`
   - `代表性反馈信号`

2. 主行动区  
   - `记录决策`
   - `决策中心`
   - `产品`
   - `模块`
   - `仓库`

3. 完成区  
   - `完成 Review`

### 推荐操作顺序

1. 先看 `Current Focus`
2. 再看 `待处理决策`
3. 如需形成判断，优先点 `记录决策`
4. 如需直接进入实体处理，走 `产品 / 模块 / 仓库`
5. 本轮 review 已看完且准备离开时，再点 `完成 Review`

### `完成 Review` 到底是什么

`完成 Review` 不是“业务已经解决”，而是：

- 结束一次 review 会话
- 写入一条 `next-step result` 到 `review_records`
- 让系统知道这次 review 已形成一个轻量结果

它当前**不是**：

- 自动创建决策
- 自动更新产品/模块/仓库
- 自动完成业务闭环

所以正确理解是：

> `完成 Review` = review 会话闭环  
> 不是 = 业务动作闭环

如果你点完后只看到 toast，这在当前实现里是正常的；你需要关注后续 reread、最近活动和你自己对“本轮 review 是否帮助推进下一步”的真实体感。

### 如何验证 `完成 Review` 真的产生了结果

当前推荐这样验证，而不是只盯着 toast：

1. 先记下点击前你本轮 review 的目标与当前页面状态
2. 点击 `完成 Review`
3. 返回 `Dashboard` 或重新进入对应 `Review`
4. 观察以下内容是否成立：
   - 页面没有报错或断链
   - `Recent Activity`、`Current Focus` 或相关 reread 区块仍能成功加载
   - 你能明确说出“这次 review 之后，我的下一步是什么”
5. 如果只出现 toast，但你完全说不清本轮 review 的后续影响，应记为“高摩擦”

当前阶段里，`完成 Review` 的主要结果是：

- review 会话被正式结束并留痕
- 后续 reread 仍应成功
- 本轮 review 的下一步应由你或后续实体动作承接

它不应该被要求呈现为“页面立刻出现一个重大业务结果”，否则会把当前系统误判为失效。

## 6.3 Weekly Review 标准用法

### 页面结构

建议把 `Weekly Review` 理解成下面 4 层：

1. `Overview`  
   看系统当前基础盘点

2. `Template Candidates + Derived Hints`  
   这是当前页面最重要的结构化下一步发现区

3. `Recent Activity + Representative Signals + Reuse Snapshot`  
   作为背景证据和辅助判断

4. 底部统一动作区  
   作为通用离场与兜底动作

### 推荐操作顺序

1. 先看 `Overview`
2. 再看 `模板候选`
3. 再看 `派生智能提示`
4. 如果模板/提示已经给出明确下一步，优先走中部 CTA
5. 若中部无法直接承接，再用底部通用动作区
6. 结束本轮 review 时，再使用 `完成 Review`

### 为什么模板候选和派生提示放在这个位置

这是当前设计有意为之：

- `Overview` 之后，用户已经完成“系统状态理解”
- 接下来最有价值的，是系统直接告诉你“下一步最值得做什么”
- 所以 `Template Candidates` 和 `Derived Hints` 被放在中上部，而不是页尾

### 如何处理与底部动作区的关系

你可以用下面这条简单规则：

- **中部 CTA 是场景专属主动作**
- **底部动作区是通用兜底动作**

也就是说：

- 看到“基于模板创建产品”，优先点它
- 看到“前往 Module Registry / 查看模块详情”，优先点它
- 如果中部没给出明确动作，再回到底部去 `记录决策` 或进入 registry

## 6.4 模板复用标准用法

### 当前模板复用到底是什么

它当前是：

- 从现有模块组合读时派生出的模板候选
- 在 `Weekly Review` 中帮助你决定是否基于现有组合创建新产品
- 在 `Product Create` 中提供预填与解释性延续

它当前不是：

- 独立模板平台
- 参数化模板系统
- 模板版本管理系统

### 正确使用路径

推荐主线：

`Dashboard -> Weekly Review -> 选择模板候选 -> 基于模板创建产品 -> Product Detail`

### 在 `Product Create` 页面你应该看到什么

如果从模板候选进入，理论上应看到：

1. 标题为“基于模板创建产品”
2. 模板来源摘要
3. 已预填的名称/描述/状态
4. 如存在能力缺口，则在创建页顶部看到 `capability_gap_hint`
5. 提交成功后，在 `Product Detail` 看到模板来源摘要和模块组合相关证据

### 如何判断模板复用是否真的有价值

你应该重点观察：

1. 是否明显减少了从零创建的输入成本
2. 是否帮你更快进入“可编辑草稿”
3. 是否在成功创建后还能看懂“这个产品是从哪个模板来的”
4. 是否比手动从空白创建更顺手

## 6.5 派生智能提示标准用法

当前正式范围只有两类提示：

1. `reuse_opportunity_hint`
2. `capability_gap_hint`

### `reuse_opportunity_hint`

含义：

- 当前模块组合已经被多个产品使用，适合直接复用

标准动作：

- 进入 `Product Create`
- 基于模板创建产品

### `capability_gap_hint`

含义：

- 当前 review 范围中出现了高频能力，但当前模板没有覆盖

标准动作：

- 进入 `Module Registry` 或 `Module Detail`
- 查看或补齐相关模块

### 正确期待

这些提示的设计目标不是“显得更智能”，而是降低你在 review 时的判断成本。

你要观察的重点不是它“酷不酷”，而是：

- 它有没有帮你更快决定下一步做什么
- 它有没有把你引到正确的 owner 页面
- 它解释得是否足够清楚

---

## 6.6 Decision Center 标准用法

### 什么时候应该去 Decision Center

以下情况建议进入 `Decision Center`：

1. 当前问题需要明确判断而不是停留在脑中
2. 你希望让某次 review 形成可复查的决策记录
3. 某个产品、模块或技术选择需要留下清晰结论

### 推荐使用方式

不是把所有想法都写成决策，而是把真正需要“经营留痕”的判断写进去。

你可以把 `Decision` 理解成：

> 对真实项目推进有影响、值得后续回看的判断

---

## 6.7 Product / Module / Repository 的标准职责

### Product

适合承接：

- 产品本身的登记与编辑
- 基于模板的下一次创造
- 查看当前产品绑定了哪些模块与仓库

### Module

适合承接：

- 补齐能力缺口
- 查看模块详情
- 决定模块是否应该进入产品绑定

### Repository

适合承接：

- 仓库登记
- 产品与仓库绑定
- 补齐“有产品但无仓库”这类结构缺口

## 7. 推荐 dry-run 主线

### 先说明：`dry-run` 不是只跑一轮

如果只跑一次，你最多只能回答“首轮能不能用”；但 `Real-Project Dry-Run` 真正要回答的是：

- 你会不会愿意继续回来使用
- review loop 会不会持续影响下一步动作
- 模板复用和派生提示会不会在第二轮、第三轮仍然有价值

因此，建议至少完成下面两轮：

1. **第一轮：首轮可用性验证**
   - 关注“能不能进入、能不能理解、能不能走通”
2. **第二轮：持续使用意愿验证**
   - 关注“我是否愿意再按同样路径回来使用”

如果条件允许，最好补一轮第三轮：

3. **第三轮：回访 reread 验证**
   - 关注“前一轮形成的结果，现在还能不能被成功 reread 和继续消费”

## 7.1 最小主线 A：日常推进

推荐这样走一轮：

1. 打开 `Dashboard`
2. 进入 `Daily Review`
3. 阅读当前焦点与待处理决策
4. 选择一个真实问题，进入 `Decision Center` 或实体页
5. 完成一次真实判断或一次真实回流
6. 返回 `Dashboard`
7. 结束本轮使用

目标不是“点完所有按钮”，而是观察：

- 这条路径是否自然
- 是否帮你更快推进真实项目
- 返回 `Dashboard` 或 reread 后，你是否能清楚感知这轮 review 的后续承接

### A 线机械判定标准

完成这一轮后，建议你逐项回答：

- 是否真的从 `Dashboard` 进入，而不是直接绕到列表页
- `Daily Review` 是否帮助你更快判断“今天最该推进什么”
- 你是否进入了一个正式承接位：`Decision / Product / Module / Repository`
- 你是否完成了一次真实判断或真实回流，而不是只浏览页面
- 返回后 reread 是否成功，且未出现断链或整页错误
- 你是否愿意明天或下一次继续按这条路径使用

若前 `4` 项中有 `2` 项以上答“否”，本轮应至少记为“高摩擦”；若出现无法继续推进的逻辑断点，应记为“阻断”。

## 7.2 最小主线 B：每周盘点与下一次创造

推荐这样走一轮：

1. 打开 `Dashboard`
2. 进入 `Weekly Review`
3. 阅读 `Overview`
4. 查看模板候选
5. 查看派生提示
6. 如果存在合适模板，点“基于模板创建产品”
7. 在 `Product Create` 观察预填质量
8. 完成创建
9. 在 `Product Detail` 查看模板来源摘要、模块组合摘要和绑定区域
10. 返回 `Dashboard`

目标是回答：

- 模板是否真的缩短了创建路径
- 派生提示是否真的支撑了下一步动作
- 创建成功后 reread 是否仍然稳定

### B 线机械判定标准

完成这一轮后，建议你逐项回答：

- `Weekly Review` 中是否真的出现模板候选或成功空态
- 是否存在单值 active candidate 或明确的成功空态
- 是否真的出现派生提示或成功空态
- 你是否通过 `templateCandidateId` 进入了可编辑预填创建页
- 预填是否明显减少了从空白创建开始的成本
- 创建成功后，`Product Detail` 是否能看到模板来源摘要、模块组合摘要与 binding 相关证据
- 返回 `Dashboard / Review / Product Detail / ReuseSummary` 后，reread 是否成功
- 若出现成功空态或“无统计变化”，你是否能区分这属于正常结果，而不是误判为失败

如果这条主线只走通了“进入创建页”，但你无法在创建成功后看懂来源与回流证据，应至少记为“高摩擦”；如果创建、回流或 reread 断裂，应记为“阻断”。

## 7.3 推荐第三轮：回访验证

如果你已经完成 A 线和 B 线，建议再补一轮“回访验证”：

1. 隔一段时间再次打开 `Dashboard`
2. 再次进入 `Daily Review` 或 `Weekly Review`
3. 观察前一轮产生的结果是否还能被 reread
4. 判断你是否仍然愿意按同一路径继续使用

这一轮重点不是新增动作，而是验证：

- 前一轮留下的结果现在还能不能被看见
- 你是否仍然能理解系统当前告诉你的“下一步是什么”
- PSCO 是否已经开始形成一种可重复的经营节奏

## 7.4 通过 / 高摩擦 / 阻断 的建议裁决

### 可判为“通过”

当以下条件大体同时成立时，本轮 `dry-run` 可判为通过：

- 你能自然从 `Dashboard` 进入
- 至少一条主线能完整走通
- 至少一次真实判断或真实创建被完成
- reread 成功，且你能看懂回流结果
- 你愿意下一次继续按相同主线使用

### 可判为“高摩擦但可继续”

当以下情况出现时，可记为高摩擦但继续：

- 你能走通主线，但经常需要停下来猜测按钮语义
- `完成 Review`、成功回流或 reread 的感知偏弱
- 页面没有报错，但你需要绕路才能完成动作

### 应判为“阻断并暂停正式 dry-run”

出现以下任一情况时，建议视为阻断：

- 无法从 `Dashboard` 稳定进入 review
- review 无法承接到正式 owner 页
- 创建、返回或 reread 断裂
- 模板来源、提示结果或绑定证据无法复读
- 你无法继续推进真实项目，只能停在浏览状态

## 9. 什么叫顺畅，什么叫高摩擦

### 9.1 顺畅

可以判为顺畅的典型信号：

- 你知道应该从哪个页面进入
- 页面里的主动作是清楚的
- 回流后你能看懂刚才发生了什么
- 你愿意第二次再按同样路径使用

### 9.2 高摩擦

可以判为高摩擦的典型信号：

- 不知道该点哪里
- 点完后不知道后续影响是什么
- 从一个页面跳到另一个页面后丢失上下文
- 成功了但你感知不到成果
- 你为了完成一件事必须绕很多路

### 9.3 阻断

可以判为阻断的典型信号：

- 功能根本无法使用
- 页面返回链断裂
- 创建/回流结果不一致
- 模板来源、提示或绑定证据无法复读
- 使用过程中出现无法继续推进的逻辑断点

## 10. 反馈记录建议格式

建议你在真实使用后，按下面格式给我反馈：

### 10.0 基础元信息

- 使用日期
- 第几轮：第一轮 / 第二轮 / 第三轮
- 使用环境说明
- 本轮主线：A 线日常推进 / B 线每周盘点 / 回访验证

### 10.1 使用背景

- 本次使用的真实项目是什么
- 本次使用是日常推进还是每周盘点
- 你本来想解决什么问题
- 开始前你预期会完成什么动作
- 开始前系统的大致状态是什么

### 10.2 实际路径

- 你从哪个页面进入
- 实际走了哪些页面
- 最后停在什么地方
- 哪一步是主动作
- 哪一步出现犹豫或绕路

### 10.3 正向感受

- 哪一步最顺
- 哪一步最有帮助
- 哪个提示或预填最有价值
- 哪个 reread 结果最让你确认“刚才真的发生了事”

### 10.4 高摩擦点

- 哪一步最绕
- 哪一步最难理解
- 哪一步成功了但你没有感知
- 哪一步虽然没报错，但你不愿意下次再这么走

### 10.5 阻断项

- 哪些地方直接影响你继续使用
- 哪些问题如果不修，就不适合继续 `dry-run`
- 如果存在阻断，阻断发生在哪条主线、哪个页面、哪个动作之后

### 10.6 最终判断

- 你是否愿意继续围绕 PSCO 使用
- 它是否真的帮助推进真实项目
- 下一步最优先要修的是什么
- 本轮结论应判为：通过 / 高摩擦但可继续 / 阻断
- 你是否建议进入下一轮，还是应先修复问题再继续

### 10.7 证据位置

- 哪些页面或区块可以复读本轮结果
- 是否有截图、页面文字、记录项或明显状态变化可作为证据
- 若出现成功空态，它出现在哪个正式挂接位

## 11. 当前手册的关键提醒

在你开始 `dry-run` 前，我最希望你带着这 5 个意识去用：

1. **从 Dashboard 进入，而不是把 PSCO 用成散装 CRUD 集合**
2. **把 Daily Review 当“今日推进分诊”，把 Weekly Review 当“阶段盘点与下一次创造准备”**
3. **把 Decision 当正式经营留痕，而不是普通备注**
4. **把 Template Reuse 和 Derived Hints 当支撑动作判断的辅助层，而不是独立平台**
5. **把“完成 Review”理解为 review 会话闭环，而不是业务已自动闭环**

## 12. 最终说明

这份手册不是为了证明 PSCO 已经完美，而是为了让真实 `dry-run` 更接近它当前设计的真实意图。

如果真实使用后你发现：

- 你根本不愿意按这条主线走
- 你总想绕开某些页面
- 某些设计意图在实际使用中没有价值
- 某些按钮的语义和你的真实心智完全不一致

那恰恰说明 `dry-run` 达到了目的。

因为 `Real-Project Dry-Run` 的真正价值，不是证明“当前设计没问题”，而是让我们知道：

> **PSCO 到底能不能在真实项目里被持续使用，并真正帮助推进下一次创造。**
