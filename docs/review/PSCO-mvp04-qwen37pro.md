## 1. Dry-Run 反馈的核心信号解读

### 1.1 四轮反馈的结构性诊断

用户完成了四轮真实使用，覆盖了从空态首访到 Daily Review 闭环的完整路径。我将四轮反馈的核心信号提炼如下：

| 轮次 | 主线 | 核心发现 | 严重程度 | 根因归类 |
| --- | --- | --- | --- | --- |
| feedback_01 | 空态首访 → Onboarding | "开始首轮录入"按钮空态无响应，阻塞首轮使用 | 🔴 阻断 | 冷启动设计缺陷 |
| feedback_02 | 绕道 Product Registry → 回到 Onboarding | Onboarding 六步表面是逻辑链，实际是四个独立实体的并列创建；先创建产品后回访才恢复正常 | 🟡 高摩擦 | 引导逻辑与底层模型不匹配 |
| feedback_03 | Onboarding 完成后验证各模块 | 所有实体需在各详情页手动关联，切换频繁；Dashboard 误标已消费决策为"待决策" | 🟡 高摩擦 | 实体关联摩擦 + 状态语义不一致 |
| feedback_04 | Daily Review → Decision 闭环 | 决策详情页无操作入口可推进状态，Dashboard / Daily Review 持续提示"待处理"但无法处理 | 🔴 阻断 | 经营回路闭环断裂 |

**结构性诊断：**

四轮反馈中 2 轮出现阻断，2 轮出现高摩擦。但这些问题不是孤立的"bug"，而是指向同一个根本性问题：

> **PSCO 当前的设计是"以数据模型为中心"，而不是"以用户经营动作为中心"。**

具体表现为：

1. **Onboarding 的"假逻辑链"**：引导用户按"产品 -> 仓库 -> 模块 -> 决策"的顺序创建，但底层数据模型是四个独立实体的并列 CRUD。用户期望的是"一站式创建产品及其关联"，实际得到的是"在四个独立页面间切换"。

2. **Decision 的"假 pending"**：Decision Detail 完成模块关联后，系统仍显示"待决策"。这是因为 Decision 的 status 字段未自动更新，或未提供"收口"动作。用户期望的是"完成关联 = 决策已消费"，实际得到的是"需要手动更新 status 或等待系统自动判断"。

3. **实体关联的高摩擦**：Module/Decision/Product/Repository 是并列隔离关系，需要在各详情页手动切换执行关联。用户期望的是"以产品为中心，一站式管理其仓库、模块、决策"，实际得到的是"以实体为中心，需要理解底层数据模型才能高效使用"。

## 2. 当前系统的结构性问题诊断

### 2.1 问题一：战略定位与实际交付的根本性错位

**当前定位：** 个人软件公司的经营与资产系统（资产登记 + 决策留痕 + 基础复用反馈）

**用户期望：** 支撑"科学实验 workflow"，帮助发现需求、找到用户、构建产品、探索迭代；以 agent 维护为主，web 端主要展示

**错位分析：**

PSCO 当前的设计是"以数据模型为中心"，而不是"以用户经营动作为中心"。具体表现为：

1. **实体模型驱动 vs 经营动作驱动**
   - 当前：Module/Decision/Product/Repository 是四个独立实体，各自有 CRUD
   - 期望：以"产品"为中心，一站式管理其仓库、模块、决策、反馈

2. **记录型系统 vs 协调型系统**
   - 当前：PSCO 主要做"记录"——登记资产、留痕决策、展示反馈
   - 期望：PSCO 应做"协调"——帮助发现机会、验证需求、加速迭代

3. **web-first vs agent-first**
   - 当前：PSCO 以 web 端为主要交互界面，用户在各详情页间手动切换
   - 期望：PSCO 应以 agent 维护为主，web 端主要展示和必要操作

### 2.2 问题二：经营回路的"假闭环"

**当前状态：**

- Dashboard -> Daily Review -> Decision -> Update 的最小经营回路已建立
- 但 Decision 的 status 字段未与实际动作联动，形成"假 pending"
- Dashboard Current Focus 只判断 status，不判断"是否已完成关联"

**根因分析：**

经营回路的设计是"以状态字段为中心"，而不是"以实际动作为中心"。具体表现为：

1. **Decision 的 status 字段是手动维护的**
   - 用户需要手动更新 status，或等待系统自动判断
   - 但系统不判断"是否已完成关联"，只判断 status

2. **Dashboard Current Focus 的判断逻辑过于简单**
   - 只判断 status = "proposed"，不判断"是否已完成关联"
   - 形成"假 pending"，破坏用户信任

### 2.3 问题三：工程化深度不足

**当前状态：**

- PSCO 所有信息维护均由用户手动填写文本描述
- 新增仓库但未触及仓库源码
- 新增模块但未管理模块版本
- 用户感觉"在设计良好的框架下书写文本"

**根因分析：**

v0.1 定位为"资产登记 + 决策留痕"，未深入真实工程集成。具体表现为：

1. **未与 Git/CI/CD/版本管理形成自动化联动**
   - 用户需要手动维护仓库 URL、模块版本等信息
   - 系统不自动识别仓库状态、分支、PR

2. **未支撑"科学实验 workflow"**
   - 无机会管理、无需求验证流程
   - 无法支撑"想法 -> 假设 -> 实验 -> 验证 -> 反馈 -> 迭代"

## 3. 下一阶段推进方向建议

基于上述诊断，我建议 mvp0.4 的核心主题收敛为：

> **闭环修复 + 协调方式升级 + 科学实验 workflow 最小承接**

### 3.1 方向 A：闭环修复（短期 P0）

**目标：** 修复 onboarding 冷启动与 Decision 状态闭环断裂，确保 phase01-09 已交付能力能真正被消费。

**范围：**

1. **修复 Onboarding 冷启动断裂**
   - 修复"开始首轮录入"按钮无响应问题
   - 明确 onboarding 流程的前置条件，避免"引导 -> 阻断 -> 用户绕行 -> 引导才生效"的摩擦路径
   - 考虑提供"完全空态"下的 onboarding 引导，或明确告知用户需要先创建产品

2. **修复 Decision 状态闭环断裂**
   - 明确 Decision "待决策"标识的语义
   - 提供"收口"动作（如"标记为已消费"）或自动更新机制（如完成关联后自动更新 status）
   - 优化 Dashboard/Daily Review 的"待处理"判断逻辑，避免"假 pending"

**进入方式：** 通过 `fix*` workflow 推进

**优先级：** P0（阻断项）

### 3.2 方向 B：协调方式升级（中期 P1）

**目标：** 将 PSCO 的协调方式从"web 端手动切换"升级为"agent 维护为主 + web 展示为辅"。

**范围：**

1. **提供 agent 友好的 API/合同**
   - 基于现有 `.proto + ConnectRPC` 主线，提供 agent 可直接消费的 API
   - 支持 Cursor/Trae/Codex 等 agent IDE 直接调用 PSCO API
   - 提供 agent 友好的错误语义与文档

2. **优化 web 端的"必要操作"入口**
   - 将"在各详情页间手动切换"的交互模式，收敛为"以产品为中心"的聚合入口
   - 提供"一站式创建产品及其关联"的聚合页面（如"创建产品 + 仓库 + 模块 + 决策"）
   - 减少用户需要理解底层数据模型的认知负担

3. **统一维护跨项目的规范、约束、机制、技术栈**
   - 将 PSCO 自身的规范、约束、机制、技术栈作为"资产"进行管理
   - 提供"项目模板"功能，新项目可直接基于统一基线开始
   - 这与 PSCO 的"资产复用"定位高度契合

**进入方式：** 通过新 `phase*` workflow 推进（如 `phase10_agent_first_coordination_upgrade`）

**优先级：** P1（战略级）

### 3.3 方向 C：科学实验 workflow 最小承接（长期 P2）

**目标：** 最小化承接"想法 -> 假设 -> 实验 -> 验证 -> 反馈 -> 迭代"的科学实验 workflow。

**范围：**

1. **引入"机会"（Opportunity）实体**
   - 承接"发现需求、找到用户"的环节
   - 与 Product/Module/Decision 形成关联
   - 支撑"想法 -> 假设"的阶段

2. **引入"实验"（Experiment）实体**
   - 承接"验证需求、构建产品"的环节
   - 与 Opportunity/Product 形成关联
   - 支撑"实验 -> 验证"的阶段

3. **强化 Feedback 的"验证"语义**
   - 将 Feedback 与 Experiment 形成关联
   - 支撑"反馈 -> 迭代"的阶段

**进入方式：** 通过新 `phase*` workflow 推进（如 `phase11_scientific_experiment_workflow_foundation`）

**优先级：** P2（战略级）

**注意：** 这个方向涉及新增长期核心实体，需要谨慎评估投入产出比。建议先通过方向 A 和 B 修复当前问题，再考虑是否进入方向 C。
