## 2. 对 `mvp03-DPv4pro` 建议路线的重新评估

### 2.1 原建议回顾

`mvp03-DPv4pro.md` 建议的 mvp0.3/mvp0.4 路线是：

```
phase08: Venture & Strategic Context
phase09: Decision Intelligence
phase10: AI Context Enhancement
```

当时的判断逻辑是：经营闭环已建立 → 引入战略容器（Venture）→ 让决策可检索可引用 → 最后引入 AI 增强。

### 2.2 Dry-Run 反馈对这条路线的冲击

Dry-run 反馈暴露了三个关键事实，对上述路线形成冲击：

**冲击一：当前系统的"经营闭环"实际上并未真正闭合。**

用户在 feedback_04 中明确指出：决策创建后，Dashboard 和 Daily Review 持续提示"待处理"，但决策详情页没有操作入口可推进状态。这意味着 `Feedback → Decision → Update` 的最小回路在真实使用中并未形成可感知的闭环——决策只能"创建"和"查看"，不能"推进"和"完成"。

**冲击二：用户的核心痛点不是"缺少战略容器"，而是"系统没有触及真实开发过程"。**

Venture 解决的是"为什么做"的问题，但用户当前的核心痛点不是"不知道为什么做"，而是"系统只记录文本，不连接真实代码、仓库和开发过程"。在解决后一个问题之前引入 Venture，很可能只是增加了一个"战略文本记录器"，而不会实质改善用户体验。

**冲击三：用户对未来工作方式的预判（agent 维护为主）与当前"手动点击关联"的交互模式存在根本性矛盾。**

如果 PSCO 的未来维护主体是 agent，那么当前的重点不应该是"增加更多需要手动维护的实体类型（如 Venture）"，而应该是"建立 agent 可编程访问的接口和上下文协议"。

### 2.3 重新校准后的优先级判断

基于以上冲击，我对原建议路线进行重新排序：

| 原建议 | 原优先级 | 重新评估 | 新优先级 | 理由 |
| --- | --- | --- | --- | --- |
| Venture & Strategic Context | P0 | 后移 | P2 | 当前核心痛点不在此；在解决"连接真实开发"之前引入，价值有限 |
| Decision Intelligence | P0 | 保留但调整范围 | P1 | 决策闭环断裂是真实阻断项，需优先修复；但"决策智能"需先等闭环修复 |
| AI Context Enhancement | P1 | 大幅调整方向 | P0（重新定义） | AI 增强的方向应从"辅助人类手动操作"转向"建立 agent 可编程上下文" |

**新的优先级逻辑：先修复阻断项让系统可用 → 再建立 agent 可编程接口让系统可被 agent 维护 → 再考虑扩展实体和智能能力。**

## 3. MVP0.4 的重新定位：从"智能增强"到"真实连接"

### 3.1 核心命题的重新表述

`mvp03-DPv4pro` 中我为 MVP0.3 定义的核心命题是：

> 在经营闭环已经建立的基础上，如何让 PSCO 开始"加速"用户的决策质量和资产增长速度？

经过 dry-run 反馈的重新校准，我认为 MVP0.4 的核心命题应该修正为：

> **在资产登记和经营框架已经建立的基础上，如何让 PSCO 从"文本记录系统"升级为"真正连接代码、仓库和开发过程的经营系统"？**

这个命题有三个子问题：

1. **连接层**：如何让 PSCO 不只是记录"我有一个仓库叫 X"，而是真正触及仓库、代码和版本？
2. **闭环层**：如何让决策、review 和实体更新形成真正可感知的闭环，而非"创建后只能查看"？
3. **Agent 层**：如何让 PSCO 具备 agent 可编程访问的能力，使未来的日常维护由 agent 而非人工点击完成？

### 3.2 三个阶段的演进模型修正

Dry-run 反馈让我重新审视了 PSCO 的演进阶段。原模型是：

```
MVP0.1: Asset Registry（资产登记系统）
MVP0.2: Operating System（经营系统）
MVP0.3: Intelligence-Enhanced Growth System（智能增强的增长系统）
```

修正后的模型：

```
MVP0.1: Asset Registry（资产登记系统）
  "我记录了什么资产" ✅ 已完成

MVP0.2: Operating Awareness（经营感知系统）
  "我能看见资产状态、复用信号和经营焦点" ✅ 已完成（phase01~09）

MVP0.3: Connected Operating System（连接型经营系统）—— 对应 mvp0.2 阶段二原目标
  "我的资产登记连接到了真实代码和仓库，决策能形成可感知闭环" ← 当前应进入

MVP0.4: Agent-Native Operating System（Agent 原生经营系统）
  "系统主要由 agent 维护，我通过 Web 查看状态和进行关键决策" ← 远期目标
```

**关键变化：在"经营感知"和"智能增强"之间，插入了一个"连接型经营系统"阶段。这个阶段解决的是 dry-run 反馈中暴露的最核心问题——PSCO 与真实开发过程的脱节。**

## 4. 主线 A：闭环修复（阻断项修复）

### 4.1 为什么必须先修阻断项

Dry-run 暴露了两个阻断项和一个高摩擦项，它们直接影响系统的基本可用性：

1. **Onboarding "开始首轮录入"按钮空态无响应**（feedback_01）：这是首访用户的第一个交互，直接阻断
2. **决策闭环缺失**（feedback_04）：决策创建后无操作入口推进状态，Dashboard / Review 持续误报"待处理"
3. **Dashboard Current Focus 误标已消费决策**（feedback_03）：状态判断逻辑存在缺陷

这些不是"功能增强"，而是"功能修复"。在进入任何新能力建设之前，必须先让已有功能在真实使用中形成闭环。

### 4.2 闭环修复的最小范围

| 问题 | 根因推测 | 修复方向 | 优先级 |
| --- | --- | --- | --- |
| Onboarding 按钮空态无响应 | 空态下 Onboarding 流程可能依赖某些已存在的数据（如至少一个 module/product）才能推进下一步 | 检查 Onboarding 状态机的空态分支，确保纯空态下六步流程可独立走通 | P0 |
| 决策无操作入口推进状态 | Decision 实体缺少状态流转机制（如 proposed → accepted → implemented 等），当前只有 CRUD 无生命周期 | 为 Decision 引入最小状态机（proposed / accepted / rejected / superseded），在详情页提供状态变更入口 | P0 |
| Dashboard 误标"待决策" | Current Focus 的"待决策"判断逻辑可能基于"决策存在"而非"决策状态为 pending/proposed" | 修正 Current Focus 的筛选条件，已 accepted/rejected 的决策不再标记为"待决策" | P0 |
| Onboarding 六步是"假逻辑链" | 六步之间没有传递创建结果（如第一步创建的产品 ID 未自动填入第二步的仓库绑定） | 在 Onboarding 流程中建立步骤间的数据传递：产品 → 仓库绑定 → 模块 → 决策，让每一步自动关联上一步的创建结果 | P1 |

### 4.3 闭环修复的明确非目标

- ❌ 不做完整的 Decision 生命周期工作流引擎
- ❌ 不做 Onboarding 的完全重设计
- ❌ 不引入新的实体类型
- ❌ 不改变现有 .proto 合同的主体结构

## 5. 主线 B：真实连接（从"文本描述"到"代码触及"）

### 5.1 为什么这是 MVP0.4 最核心的主线

用户的反思 4 和反思 6 直指 PSCO 当前最根本的缺陷：

> "我新增了仓库，我触及到仓库吗？我新增 module，我触及到模块源码吗？好像我仅仅只是一个文本描述者，而不是一个功能实现者。"

这不是一个"功能缺失"的问题，而是一个**价值定位**的问题。如果 PSCO 永远只能记录文本描述，那它就不是"Personal Software Company OS"，而是"Personal Software Company Wiki"。

**当前 PSCO 已经在 Repository Binding 中记录了仓库 URL，在 Module Registry 中记录了模块名称和版本。这些数据已经存在，但系统从未尝试"触及"它们指向的真实对象。**

### 5.2 真实连接的最小能力集

我建议在 MVP0.4 中引入以下最小连接能力，全部以"读时派生、不持久化"为原则：

| 能力 | 描述 | 数据来源 | 优先级 |
| --- | --- | --- | --- |
| **仓库元数据回显** | 在 Repository Detail 中展示仓库的基本信息（星标数、最后更新时间、主要语言），通过 GitHub API 读时获取 | 已登记的 repository URL | P0 |
| **模块源码结构预览** | 在 Module Detail 中展示关联仓库中该模块对应目录的文件结构（浅层，如 `src/`、`package.json` 等关键文件存在性），通过 GitHub API 或本地文件系统读时获取 | 已登记的 module name + 已关联的 repository URL | P1 |
| **版本与 Git Tag 关联** | 在 Module Detail 中展示该模块的 Release 版本与 Git 仓库 Tag 的对应关系 | 已登记的 release version + 已关联的 repository URL | P1 |
| **仓库活动时间线** | 在 Repository Detail 中展示最近的 commit 活动和 contributor 信息 | 已登记的 repository URL | P2 |

### 5.3 技术实现约束

1. **读时派生，不持久化**：所有连接数据在用户访问页面时实时获取（或短时缓存），不写入 PSCO 数据库。这避免了数据同步一致性问题，也保持了 PSCO 的轻量特性。
2. **GitHub API 为默认数据源**：当前阶段只对接 GitHub API（公开仓库），不引入多平台适配。GitHub API 有 60 次/小时的未认证限制，对于个人使用足够。
3. **失败优雅降级**：API 调用失败或超时时，页面回退到当前纯文本展示模式，不阻塞用户操作。
4. **不引入 OAuth**：当前阶段只访问公开仓库信息，不需要 GitHub OAuth 认证流程。
5. **不引入本地文件系统扫描**：当前阶段不做本地代码扫描，只通过 GitHub API 获取元数据。

### 5.4 真实连接的明确非目标

- ❌ 不做全自动代码扫描
- ❌ 不做代码质量分析或静态分析
- ❌ 不做 GitHub OAuth 集成
- ❌ 不做私有仓库访问
- ❌ 不做多平台（GitLab / Gitee）适配
- ❌ 不做本地文件系统监控或实时同步
- ❌ 不做代码内容的深度解析（AST、依赖图等）

## 6. 主线 C：Agent-Native 基础（为未来奠基）

### 6.1 为什么现在就要考虑 Agent-Native

用户的反思 7 明确指出：

> "由于使用 agent 开发是主流，绝大多数 PSCO 应该以 agent 维护为主，PSCO web 前端主要展示这个 Personal Software Company 实际状态，同时我通过 web 端提供的操作入口进行必要的操作管理与信息补充维护。"

这个判断与当前 AI 编程工具（Cursor、Trae、Codex）的发展趋势高度一致。但当前 PSCO 的架构完全是"人类手动点击"模式——每个实体创建、每个关联绑定、每个决策记录都需要人工在 Web 页面上操作。

**如果 PSCO 的未来维护主体是 agent，那么当前最重要的事不是"增加更多需要手动维护的实体"，而是"让 agent 能够程序化地访问和操作 PSCO"。**

### 6.2 Agent-Native 的最小基础

好消息是：PSCO 已经具备了 agent 可编程访问的技术基础——`.proto + ConnectRPC`。所有业务接口已经通过 ConnectRPC 暴露，理论上 agent 可以直接调用。

但当前缺少的是：

1. **Agent 上下文协议**：agent 需要知道"给定当前项目，PSCO 中有哪些相关资产、决策和约束"
2. **跨项目知识基线**：用户反思 8 中提到的"规范、约束、机制、技术栈"等跨项目知识，当前分散在各项目仓库中

### 6.3 Agent-Native 的最小能力集

| 能力 | 描述 | 优先级 |
| --- | --- | --- |
| **Agent Context Query API** | 提供一个 RPC，输入当前项目上下文（仓库 URL、项目路径、当前任务描述），返回 PSCO 中相关的资产、决策、模块和约束 | P0 |
| **跨项目知识基线存储** | 在 PSCO 中建立一个最小化的"全局知识"存储，用于存放跨项目通用的规范、约束、技术栈选择等 | P1 |
| **Agent 可写 API 完善** | 确保所有 CRUD 操作（创建产品/模块/决策/仓库、绑定关联、记录决策）均可通过 ConnectRPC 完成，且返回足够丰富的错误信息 | P1 |
| **Agent 上下文注入点** | 定义一个标准化的上下文注入格式（如 Markdown 片段），agent 可在开始工作时拉取 PSCO 上下文并注入到工作会话中 | P2 |

### 6.4 Agent Context Query API 的最小设计

```
// 输入：当前项目上下文
message AgentContextQueryRequest {
  string repository_url = 1;      // 当前仓库 URL
  string current_task = 2;        // 当前任务描述（可选）
  repeated string tags = 3;       // 上下文标签（如 "auth", "database", "frontend"）
}

// 输出：PSCO 中与该上下文相关的所有信息
message AgentContextQueryResponse {
  repeated ProductSummary related_products = 1;
  repeated ModuleSummary related_modules = 2;
  repeated DecisionSummary related_decisions = 3;
  repeated RepositorySummary related_repositories = 4;
  repeated GlobalKnowledgeEntry global_knowledge = 5;  // 跨项目知识
  string context_injection_markdown = 6;  // 可直接注入 agent 会话的 Markdown 片段
}
```

这个 API 的设计意图是：agent 在开始一个项目的工作时，先调用这个 API，获取 PSCO 中与该项目的所有相关上下文，然后将其注入到工作会话中。

### 6.5 Agent-Native 的明确非目标

- ❌ 不做 Agent 运行时或 Agent 编排引擎
- ❌ 不做 AI Chat 界面
- ❌ 不做自动任务分配或 Agent 调度
- ❌ 不做 Agent 行为的自动记录或审计
- ❌ 不做跨项目知识的自动提取（当前阶段由人手动维护）

## 7. 三条主线的整体推进建议

### 7.1 推荐的推进顺序

```
phase10（MVP0.4 启动 — 主线 A：闭环修复）:
  修复 Onboarding 空态阻断 + 决策闭环缺失 + Dashboard 误标

phase11（MVP0.4 — 主线 B：真实连接）:
  仓库元数据回显 + 模块源码结构预览 + 版本与 Tag 关联

phase12（MVP0.4 收口 — 主线 C：Agent-Native 基础）:
  Agent Context Query API + 跨项目知识基线 + Agent 可写 API 完善
```

### 7.2 依赖关系论证

```
phase10（闭环修复）
    │  修复阻断项，让系统在真实使用中可用
    │  为后续所有能力提供可靠的运行基础
    ▼
phase11（真实连接）
    │  让 PSCO 从"文本记录"升级为"连接真实代码和仓库"
    │  依赖：phase10 确保基础功能可用，连接数据才有意义
    │  为 phase12 的 Agent Context Query API 提供真实数据源
    ▼
phase12（Agent-Native 基础）
    │  建立 agent 可编程访问的接口和上下文协议
    │  依赖：phase11 的连接数据使 Agent Context Query 返回的信息更有价值
    │  依赖：phase10 的闭环修复使 agent 写入的数据能被正确消费
```

### 7.3 为什么这个顺序

1. **闭环修复必须先做**：如果基础功能在真实使用中就是断裂的，任何新能力都是建立在不可靠的基础上
2. **真实连接先于 Agent-Native**：Agent Context Query API 需要返回"连接后的真实数据"才有价值。如果 PSCO 仍然只有文本描述，agent 获取的上下文也只是"一些文本标签"，价值有限
3. **Agent-Native 基础最后**：它是对前三层（登记 + 经营 + 连接）的程序化访问层，必须在数据层和连接层成熟后才能真正产生价值
4. **Venture / Decision Intelligence / AI Context Enhancement 继续后移**：在"连接真实开发"和"agent 可编程访问"这两件事没有解决之前，扩展实体类型和智能能力的前置条件不成熟

### 7.4 与 `mvp03-DPv4pro` 建议的对比

| 维度 | mvp03-DPv4pro 建议 | 本次重新校准 | 变化原因 |
| --- | --- | --- | --- |
| 第一优先级 | Venture & Strategic Context | 闭环修复 | Dry-run 发现阻断项，必须先修 |
| 第二优先级 | Decision Intelligence | 真实连接 | Dry-run 发现 PSCO 与真实开发脱节，是比"决策智能"更根本的问题 |
| 第三优先级 | AI Context Enhancement | Agent-Native 基础 | Dry-run 发现未来维护主体是 agent，AI 增强的方向需要重新定义 |
| Venture | 立即进入 | 后移到 mvp0.5+ | 用户核心痛点不在此 |
| Decision Intelligence | 立即进入 | 后移到 mvp0.5+ | 需先修复决策闭环，再谈智能 |
| AI Context Enhancement | 作为 mvp0.3 收口 | 重新定义为 Agent-Native 基础 | 方向从"辅助人类手动操作"转向"建立 agent 可编程上下文" |

## 8. 对用户八点反思的逐条回应

### 8.1 反思 1："PSCO 是精良产品，但细节未形成功能闭环"

**回应**：同意。这恰好是主线 A（闭环修复）要解决的问题。当前系统的架构设计是优秀的，但在"状态机"维度存在缺失——Decision 只有 CRUD 没有生命周期，Onboarding 六步之间没有数据传递。这些问题不涉及架构变更，属于"最后一公里"的实现补全。

### 8.2 反思 2："Onboarding 六步是假逻辑链"

**回应**：同意。这是设计层面的问题，不是 bug。当前 Onboarding 的设计意图是"引导用户完成四类实体的首轮录入"，但没有实现步骤间的数据传递。修复方案已在 §4.2 中给出——在六步之间建立创建结果的自动传递。

### 8.3 反思 3："实体间并列隔离，手动关联摩擦大"

**回应**：这个问题的根源在于 PSCO 的底层设计哲学——保持实体间的独立性，通过显式关联（Binding / LinkDecisionToTarget）建立关系。这个设计哲学本身是正确的（保证了最大的灵活性），但当前缺少"引导式关联"——在创建完成后，系统应该主动提示"你是否要将这个新模块绑定到已有产品？"而不是让用户自己去各个详情页手动操作。这可以在主线 A 中作为一个改进项引入。

### 8.4 反思 4："PSCO 只是文本描述者"

**回应**：这是整个反馈中我最认同的一点，也是主线 B（真实连接）要解决的核心问题。当前的 PSCO 确实只是"结构化文本记录系统"。但好消息是：Repository URL 和 Module 名称已经在系统中，连接真实数据的技术基础（GitHub API）已经成熟，只是系统从未尝试去"触及"它们。这不是一个需要推翻重来的问题，而是一个"补上缺失的一层"的问题。

### 8.5 反思 5："我到底想要什么？"

**回应**：这是整个反馈中最深刻的一段。你的自我描述——"独立开发者，没有现成用户和需求，必须一手抓市场，以科学实验式 workflow 探索外部需求"——清晰地定义了 PSCO 应该服务的核心场景。

当前 PSCO 的设计假设是"用户已经有了明确的产品和模块，需要记录和经营它们"。但你的真实场景是"用户正在探索和验证，需要一套系统支撑这个探索过程"。

这两个场景的差异是根本性的：
- "记录型"场景需要的是：CRUD、分类、检索、回顾
- "探索型"场景需要的是：假设管理、实验设计、结果追踪、迭代决策

**PSCO 在"记录型"场景下已经做得不错，但在"探索型"场景下几乎完全空白。** 这不应该在 MVP0.4 中立即解决（因为"探索型"场景需要更复杂的设计），但必须作为 MVP0.5+ 的核心方向被明确记录下来。

### 8.6 反思 6："PSCO 处于生产经营与工程化的中间地带"

**回应**：同意。这反映了 PSCO 当前的一个结构性矛盾——它试图同时服务"经营"和"工程"两个维度，但两个维度都不深入。

我的建议是：**短期优先深化"工程化"维度**（主线 B：真实连接），因为这是 PSCO 作为"软件公司 OS"的独特价值所在；"生产经营"维度（多产品运行数据聚合、支付、客服等）可以在后续通过独立产品解决，PSCO 只需要提供统一的数据聚合接口。

### 8.7 反思 7："未来 PSCO 应以 agent 维护为主"

**回应**：完全同意。这是主线 C（Agent-Native 基础）的核心理由。当前 PSCO 的交互模式是"人类手动点击"，但考虑到 AI 编程工具的普及和 agent 工作流的成熟，PSCO 的维护主体必然会从"人"转向"agent"。主线 C 的目标不是现在就实现完整的 agent 自主维护，而是先建立 agent 可编程访问的基础设施，为未来的全面转型做准备。

### 8.8 反思 8："跨项目知识应集中维护"

**回应**：同意。这是一个非常实际的需求。当前你每次开新项目都需要从旧项目复制粘贴规范、约束和技术栈配置。PSCO 作为"Personal Software Company OS"，理应承担"全局知识基线"的角色。

这个能力被纳入主线 C 的 P1 优先级——在 Agent-Native 基础设施中建立一个最小化的跨项目知识存储。但需要注意的是：当前阶段由人手动维护这些知识，不做自动提取。

## 10. MVP0.4 的度量与验收标准

### 10.1 对 MVP0.4 整体的验收问题

当 MVP0.4 完成时，系统应能回答以下问题：

1. 用户能否从空态开始，顺畅完成 Onboarding 六步，且每一步的结果自动关联到上一步？
2. 用户能否在决策详情页推进决策状态（如从 proposed 到 accepted），且 Dashboard 和 Review 不再误报已消费的决策？
3. 用户能否在 Repository Detail 和 Module Detail 中看到从真实仓库获取的元数据（而非仅文本描述）？
4. Agent 能否通过单一 API 调用获取与当前项目相关的所有 PSCO 上下文？
5. 跨项目知识（规范、约束、技术栈）是否能在 PSCO 中集中维护，并被 agent 查询到？

### 10.2 各主线的独立 DoD

#### 主线 A（闭环修复）DoD

- 空态 Onboarding 六步可独立走通，无需先创建产品再回访
- Onboarding 步骤间自动传递创建结果（产品→仓库→模块→决策）
- Decision 详情页具有状态变更入口（proposed / accepted / rejected / superseded）
- Dashboard Current Focus 不再误标已 accepted/rejected 的决策
- Daily Review 不再将已消费决策标记为"待处理"

#### 主线 B（真实连接）DoD

- Repository Detail 展示 GitHub 仓库元数据（星标、最后更新时间、主要语言）
- Module Detail 展示关联仓库中模块目录的浅层文件结构
- Module Release 版本与 Git Tag 的对应关系可查看
- 所有连接数据读时获取，不持久化到 PSCO 数据库
- GitHub API 失败时页面优雅降级，不阻塞用户操作

#### 主线 C（Agent-Native 基础）DoD

- `AgentContextQuery` RPC 可用，输入仓库 URL 返回相关资产、决策和模块
- 跨项目知识基线可手动创建和维护（最小字段：title / content / tags）
- 所有 CRUD 操作均可通过 ConnectRPC 完成，返回标准化错误信息
- `AgentContextQuery` 返回的 Markdown 片段可直接注入 agent 工作会话

## 11. 风险与缓解

| 风险 | 级别 | 缓解措施 |
| --- | --- | --- |
| GitHub API 限流导致连接数据不可用 | 🟡 中 | 读时获取 + 优雅降级；60 次/小时对于个人使用足够；可加短时内存缓存 |
| "真实连接"被过度工程化（演变为代码分析平台） | 🟡 中 | 严格限定为"元数据回显"，不做 AST 解析、不做依赖分析、不做代码质量 |
| Agent-Native 基础过早优化（在 agent 实际使用前做了太多假设） | 🟡 中 | 只做最小 API 和上下文格式定义；不做 agent 运行时、调度或编排 |
| 闭环修复引入 Decision 状态机后，与既有 Review 流程产生冲突 | 🟢 低 | Decision 状态机只加 4 个状态，Review 流程只需修正筛选条件，不涉及架构变更 |
| 跨项目知识基线被过度设计（演变为 Wiki 或知识库） | 🟢 低 | 严格限定为最小字段（title / content / tags），不引入分类、版本、权限等复杂特性 |

## 12. 最终结论

### 12.1 一句话总结

> **MVP0.4 的任务，不是继续扩展 PSCO 的实体宽度或智能高度，而是先修复真实使用中暴露的闭环断裂，再让 PSCO 从"文本记录系统"升级为"连接真实代码和仓库、可被 agent 程序化访问的经营系统"。**

### 12.2 三条主线

1. **闭环修复**：修复 Onboarding 阻断、决策闭环缺失和 Dashboard 误标，让已有功能在真实使用中形成可感知的闭环
2. **真实连接**：通过 GitHub API 读时获取仓库和模块的元数据，让 PSCO 从"文本描述者"升级为"连接真实开发过程的系统"
3. **Agent-Native 基础**：建立 Agent Context Query API 和跨项目知识基线，为未来 agent 维护为主的模式奠定基础

### 12.3 推进顺序

```
phase10: 闭环修复（阻断项修复）
phase11: 真实连接（仓库元数据 + 模块结构 + 版本关联）
phase12: Agent-Native 基础（Agent Context Query API + 跨项目知识基线）
```

### 12.4 核心原则

1. **先修后建**：阻断项修复优先于任何新能力建设
2. **连接优先于扩展**：在增加新实体类型之前，先让已有实体连接真实世界
3. **Agent-Native 优先于 AI-Enhanced**：在让 AI 辅助人类操作之前，先让 PSCO 具备 agent 可编程访问的基础
4. **读时派生优先于持久化**：连接数据不写入 PSCO 数据库，保持系统轻量
5. **继续坚持技术栈冻结**：不引入新基础设施、不引入第二套事实源
6. **"探索型"场景是 mvp0.5+ 的核心方向**：当前阶段先记录，不做完整实现

### 12.5 对 `mvp03-DPv4pro` 的最终校准说明

`mvp03-DPv4pro.md` 是在没有真实使用数据的情况下做的推演。Dry-run 反馈提供的关键新信息——PSCO 与真实开发过程脱节、决策闭环断裂、未来维护主体是 agent——让我重新校准了优先级。

原建议的 Venture → Decision Intelligence → AI Context Enhancement 路线在逻辑上是自洽的，但它回答的问题是"如何在已有基础上增加智能"。而 Dry-run 反馈揭示的真正问题是"已有基础本身在真实使用中是否成立"。

**因此，MVP0.4 的方向从"向上叠加智能"调整为"向下扎根连接"。** 这不是否定之前的判断，而是在获得新证据后做出的理性校准。
