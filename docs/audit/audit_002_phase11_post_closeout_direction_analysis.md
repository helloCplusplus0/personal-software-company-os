# Audit 002 Analysis - phase11 收口后四实体语义对齐与 agent 渠道下一步方向仲裁

## 1. 审计摘要
- 对应问题：`audit_002`
- 审计级别：`P1`
- 是否建议进入后续动作：是
- 最终去向：`escalate-phase`

## 2. 模块目标复述
- 该模块要解决什么问题：
  在 `phase11` 正式收口之后，为 `PSCO` 明确下一阶段的单一主交付方向，并判断四实体语义澄清对前端现状的影响程度，以及 agent 渠道是否应继续沿只读消费深化。
- 该模块服务哪些角色：
  阶段规划者、前端实现者、Go backend 能力面维护者、agent 消费方。
- 当前正式定位是什么：
  `PSCO-mvp05-summarize-feedback.md` 已冻结：`mvp0.5` 的中心任务是让 PSCO 成为 agent 可稳定消费的项目上下文系统，而不是直接进入完整 agent 平台建设；`phase11` 已完成根级治理与最小只读项目上下文导出。

## 3. 当前现状结论
- 当前设计中已经合理的部分：
  - `phase11` 已明确四实体语义：`Product` 是经营目标与交付容器，`Repository` 是代码仓库身份对象与项目锚点，`Module` 是可复用能力资产，`Decision` 是规则、约束、选择与依据的索引对象
  - 前端四实体切片已经形成稳定边界，且未直接长出与 `phase11` 冻结语义冲突的第二套实体体系
  - agent 已获得最小只读消费入口，`GetProjectContext / ExportProjectContext` 与根级真相源治理已完成 dogfooding
- 当前设计中存在疑问的部分：
  - 前端四实体页面与类型注释主要仍对齐 `phase02 ~ phase04` 的正式规格，而不是 `phase11` 对语义层的再解释
  - 页面文案、空状态、解释性语言与下一步动作承接，尚未系统吸收“Module 是可复用能力资产”“Decision 是规则/约束索引对象”的新口径
  - `phase11` 交付的是只读消费基础，不是更重的 agent 消费通道，更不是受控维护能力
- 当前实现中需要重点关注的边界：
  - 四实体语义澄清不应被偷换为立刻进行 proto/schema/路由主线重构
  - 下一步若继续推进 agent 能力，仍必须遵守“先消费、后维护”的顺序
  - 若当前前端表达与 `phase11` 语义存在漂移，更适合以“语义一致性改进”而不是“大重构”承接

- 当前实现是否符合工程目标：
  符合此前各 phase 的工程目标，且当前四实体切片仍能支撑业务运行；但它们没有自动继承 `phase11` 的语义澄清，需要后续显式对齐。
- 当前实现是否符合既有冻结原则：
  基本符合。`phase11` 明确要求“只确认语义，不重写结构”，因此当前前端无需因为语义澄清立即启动结构重写。

## 5. 用户视角审计
- 问题是否成立：
  成立。即使底层结构不需要立刻改，若页面对四实体“为什么存在、当前扮演什么角色”的表达仍停留在早期口径，用户会继续把它们理解成松散 CRUD 页。
- 当前交互是否顺手：
  当前交互整体可用，尤其 detail / list / binding / review / onboarding 的返回链和只读/写入承接已经较稳定。
- 当前信息表达是否清晰：
  局部清晰，但整体还没有把 `phase11` 冻结出来的项目语义真正投射到前端阅读体验中。
- 当前反馈是否可信、完整：
  对已交付主线是可信的；对“PSCO 到底把四实体各自看成什么”这类认知问题，前端还没有形成足够强的单值表达。
- 当前体验距离最佳实践的主要差距：
  - 用户仍可能把 `Module` 当成普通模块清单，而不是可复用能力资产
  - 用户仍可能把 `Decision` 当成文本记录，而不是规则/约束索引对象
  - agent 渠道虽然已能只读消费，但人类用户在 Web 端还没有同步感受到 `phase11` 带来的认知收口

## 6. 综合审计结论
- 最终判断：
  **`phase11` 之后不应直接走向更重的 agent 通道扩张，也不应因为四实体语义澄清就立刻发起全仓重构；更合理的下一步是升级为新的 phase 级议题，在“语义一致性收口 + read-only agent consumption 深化”之间建立单一主交付。**
- 判断依据：
  1. `PSCO-mvp05-summarize-feedback.md` 已冻结：当前阶段的中心是只读消费，不是维护或重型协议扩张
  2. `phase11` 已完成的交付正是最小只读消费基础，而不是完整 agent 平台
  3. `phase11` 对四实体的冻结是“语义澄清，不做结构重构”，因此当前更像是进入“表达与交互语义收口”阶段，而不是“重写数据模型”阶段
- 当前是否值得改动：
  值得，但不适合当作局部 fix 或单点实现任务处理。
- 若不改，原因：
  不适用。
- 若要改，原因：
  若不把 `phase11` 的语义冻结继续落实到前端表达与下一阶段主交付上，`phase11` 会停留在“agent 可读、但人类前端理解未完全对齐”的半收口状态；同时，下一阶段也容易重新滑向“大而泛的 agent 平台想象”。

## 7. 最佳实践对标
- 最佳实践应是什么：
  - 四实体的语义冻结要在 Web 端、agent 只读消费与根级真相源中形成同值表达
  - 下一阶段仍围绕“先消费、后维护”推进，不跳过只读消费深化直接进入 MCP / CLI / 写回
  - 若需要重新建立方向共识，应尽量基于收敛过的内部审计而不是一上来重新开放大范围原则争论
- 当前方案与最佳实践的差异：
  当前仓库已经完成 `phase11` 的后端与根级交付，但前端语义表达和下一阶段方向说明还没有形成正式承接位。
- 是否需要完全看齐：是
- 若不完全看齐，保留差异的理由：
  允许在实现节奏上分阶段推进，但不应在方向判断上继续含混。

## 8. 候选方案对比
### 方案 A
- 做法：
  立即以 `phase11` 的新语义为依据，对前端四实体切片做一轮结构性重构，包括类型、页面组织、文案、交互与潜在数据模型同步改名。
- 优点：
  - 一次性把“语义”和“前端表达”都收口
  - 看起来最彻底
- 风险：
  - 容易把“语义澄清”误执行成“结构重构”
  - 会打断当前已稳定的切片边界和写路径承接位
  - 与 `phase11` 冻结的“当前阶段只确认语义，不重写结构”相冲突

### 方案 B
- 做法：
  直接以 `phase11` 已经建立的只读基础为跳板，继续推进 MCP / CLI / agent 写回 / 更重消费通道，先把 agent 渠道做大做全。
- 优点：
  - 能快速放大“agent 能力建设”的外显成果
  - 迎合“phase11 只是基础，还没做完整”的直觉
- 风险：
  - 直接越过 `PSCO-mvp05` 已冻结的“先消费、后维护”顺序
  - 容易在根级、前端和 agent 侧同时长出第二套语义
  - 会把当前尚未收口的前端认知问题带入更重通道

### 方案 C
- 做法：
  把下一步升级为新的 phase 级议题，单一主交付聚焦在“`phase11` 后的语义一致性收口 + read-only agent consumption 深化”，先完成前端表达与项目语义的对齐，再决定是否需要进入更重能力。
- 优点：
  - 符合 `phase11` 已冻结的语义边界与 `mvp0.5` 的只读消费主线
  - 不要求立刻推翻前端结构，但能系统收口四实体表达
  - 给下一阶段预留清晰进入条件，避免直接跳进更重 agent 通道
- 风险：
  - 需要新的 `/plan` 明确边界，否则容易再次被理解成“大而泛的后续探索”
  - 若实施时范围控制不好，可能同时吸入“语义对齐”和“重型 agent 通道”两类议题

## 9. 推荐方案
- 推荐原因：
  推荐 **方案 C**。它最符合 `phase11` 的完成形态和 `mvp0.5` 的冻结方向。
- 最小实施边界：
  1. 先在下一阶段 `/plan` 中冻结“四实体语义在前端表达层如何正式承接”
  2. 审计并收口前端四实体页面的文案、摘要、空状态、解释性说明与下一步动作表达
  3. 在保持只读前提下，继续深化 agent consumption 的消费效率与入口稳定性，而不是直接进入写回或新协议层
  4. 只有在上述内容完成后，才讨论更重消费通道或受控维护能力
- 需要保持不变的内容：
  - `phase11` 已冻结的四实体结构与只读边界
  - Go backend canonical core
  - `Project Context Foundation` 已交付的最小只读导出结果
- 明确不在本次改进范围内的内容：
  - MCP / CLI / agent 自动写回
  - 四实体 schema 重写
  - 前端变成对话式 agent 工作台
  - 再次立即发起一轮大范围专家原则争论

  - 把“前端语义一致性收口”误做成全仓重构
  - 把“agent consumption 深化”再次偷换为“直接进入完整 agent 平台”
  - 在没有新 `/plan` 的前提下，重新回到散装讨论和散装实现
- 禁止引入的新问题：
