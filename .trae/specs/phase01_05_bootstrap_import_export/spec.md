# Phase01-05 冻结冷启动、导入与导出要求 Spec

## Why

在 `phase01-01` 到 `phase01-04` 已经完成技术路线、对象动作、页面输入路径和数据合同基线冻结之后，下一步必须把 `v0.1` 的冷启动路径、导入边界和最小导出 / 备份要求冻结成单值结论。只有先明确用户如何从零开始建立基础资产、当前阶段到底支持什么导入，以及 `Local First` 在导出与备份上的最低承诺，后续 `/spec` 才不会把这些关键问题继续留空。

## What Changes

- 冻结 `v0.1` 首轮冷启动的最小建资产路径
- 冻结当前阶段的导入路径与手动录入边界
- 冻结 `Local First` 语义下的最小导出 / 备份要求
- 明确当前阶段不要求 GitHub OAuth、自动导入、自动同步或连续备份
- 明确后续 `/spec` 必须在本次边界内细化空状态、入口动作与备份交付形式

## Impact

- Affected specs: `phase01_mvp_spec_convergence`
- Affected code: 当前无代码改动，影响后续空状态设计、表单入口、导入说明、导出能力说明与备份策略定义

## ADDED Requirements

### Requirement: 首轮冷启动路径冻结
系统 SHALL 冻结 `v0.1` 的首轮冷启动路径，使零数据用户可以从空状态出发建立第一版基础资产。

#### Scenario: 首次进入系统时的最小建资产路径
- **WHEN** 用户第一次进入系统且当前没有任何资产数据
- **THEN** 系统必须允许用户通过低摩擦手动录入依次建立 `Product`、`Module`、`Repository`、`Decision`
- **AND** 系统必须允许用户完成最小绑定关系
- **AND** 用户完成上述基础资产后必须能够进入第一版可用状态，而不是被额外前置配置阻断

### Requirement: 冷启动不依赖外部集成
系统 SHALL 明确首轮冷启动不依赖 GitHub、自动扫描、自动导入或其他外部系统集成。

#### Scenario: 判断冷启动阻断项
- **WHEN** 后续规格定义首轮录入流程
- **THEN** 不得把 `GitHub OAuth`、仓库自动导入、代码自动扫描或外部同步设为首轮必经步骤
- **AND** 必须以手动创建和手动绑定为默认前提

### Requirement: 导入边界冻结
系统 SHALL 将当前阶段的导入边界冻结为：`v0.1` 当前不冻结任何正式导入能力，首轮资产进入系统统一以手动录入为主。

#### Scenario: 判断当前阶段是否支持导入
- **WHEN** 接手者查询 `v0.1` 当前导入路径
- **THEN** 必须明确 `GitHub OAuth / 自动导入` 不进入首轮
- **AND** 必须明确 `Product`、`Module`、`Decision`、`Repository` 的首轮建立全部以手动录入完成
- **AND** 后续 `/spec` 只能在不破坏手动录入闭环的前提下，补充"非阻断型轻量导入说明"
- **AND** 不得把“后续可能支持导入”写成“当前版本已经默认支持导入”

### Requirement: 资产录入边界冻结
系统 SHALL 明确后续 `/spec` 必须区分“支持手动录入的资产”和“未来可补充导入说明的资产”，但当前阶段默认以手动录入优先。

#### Scenario: 判断资产录入方式
- **WHEN** 后续规格定义对象建立方式
- **THEN** `Product`、`Module`、`Decision` 必须保证可独立手动录入
- **AND** `Repository` 必须保证可通过手动方式建立与绑定
- **AND** 不得因为未来导入设想而削弱当前手动录入闭环

### Requirement: 最小导出要求冻结
系统 SHALL 在 `Local First = 数据所有权优先` 的前提下冻结最小导出要求，使用户能够带走自己的核心资产数据。

导出的语义定义：**面向用户带走核心资产数据**，供用户独立保存、迁移或另作它用。

#### Scenario: 判断最小导出覆盖范围
- **WHEN** 后续规格定义 `v0.1` 的导出能力
- **THEN** 导出范围至少必须覆盖 `Product`、`Module`、`Release`、`Repository`、`Decision` 及其基础绑定关系
- **AND** 导出结果必须足以支持用户理解和迁移其当前核心资产
- **AND** 不得把导出能力留成“后续再说”

### Requirement: 最小备份要求冻结
系统 SHALL 冻结 `v0.1` 的最小备份要求，使用户可以为当前实例生成可保留、可迁移的基础备份。

备份的语义定义：**面向当前实例保留与恢复**，供用户在更换设备或重新部署时恢复数据。

#### Scenario: 判断最小备份能力
- **WHEN** 后续规格定义 `v0.1` 的备份能力
- **THEN** 必须至少提供一种面向当前实例的基础备份路径
- **AND** 该备份路径必须与数据所有权、迁移能力和恢复预期保持一致
- **AND** 不要求当前阶段实现自动连续备份、多端同步或复杂灾备体系

### Requirement: 导出与备份不得依赖第三方平台
系统 SHALL 明确当前阶段的导出与备份能力不得依赖 GitHub 或其他第三方平台作为唯一前提。

#### Scenario: 判断导出与备份前提
- **WHEN** 后续规格定义导出或备份交付方式
- **THEN** 不得要求用户必须先接入 GitHub、云同步或第三方托管平台
- **AND** 必须保证在当前系统边界内存在独立完成导出 / 备份的路径

## MODIFIED Requirements

### Requirement: 后续空状态、导入说明与导出策略引用前提
后续 `/spec` 编写空状态、入口动作、导入说明、导出说明与备份策略时 SHALL 以本次冻结的冷启动、导入与导出边界为唯一上游，不得重新扩大首轮范围或把未来自动化写成当前事实。

#### Scenario: 后续冷启动与导出规格编写
- **WHEN** 后续 `/spec` 细化首轮路径、空状态、导入说明或备份策略
- **THEN** 必须引用本次冻结的边界
- **AND** 不得绕开本规格重新定义 `v0.1` 的冷启动依赖、导入优先级或导出责任
